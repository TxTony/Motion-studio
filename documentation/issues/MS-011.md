# MS-011 - Add Character import: map external skeletons to studio roles

Status **To do**. Owner **Coordinator**. This issue is authorized for investigation and specification only; implementation is not started. References: [architecture](../ARCHITECTURE.md), [current import contract](../../README.md#interchangeable-character).

## Outcome and current limit

Import a supported external humanoid GLB without requiring its original bone names to match Motion Studio. The current loader searches for eleven exact names and derives axes from the first qualifying child. Renaming alone does not solve different rest poses, local axes, intermediate bones or branching hierarchies. A static mesh without a rig cannot be made animatable by a naming map.

## Proposed solution

Keep the current eleven semantic roles as the engine boundary, independent of asset node names. Add a per-character binding profile that maps each role to an unambiguous source node identifier (glTF node index, scoped to the exact asset hash), plus rest-frame/axis corrections and a version. Preserve original model names, hierarchy, skin weights and animations. Display names/paths assist users but are not unique identifiers. Profiles must not silently bind a different file or duplicate name.

The import flow would inspect the rig, propose known correspondences, allow explicit selection/correction, validate the mapping, preview a neutral pose and deterministic movements, then activate the rig. Name matching is a suggestion only; ambiguity must be visible. Use existing selector/form/core wrappers for future UI. Save/reload the mapping as versioned JSON tied to the model fingerprint. Preserve existing self-contained GLB and file-size limits. Do not broaden existing animation JSON semantics silently.

## Reference asset and naming decision

[Cesium Man](https://github.com/KhronosGroup/glTF-Sample-Assets/tree/main/Models/CesiumMan) is the first proposed integration fixture (CC BY 4.0, retain attribution and logo notice). Its source skeleton was inspected in the prior discussion; it uses names such as Skeleton_torso_joint_1 and Skeleton_arm_joint_L__4_. No asset has yet been downloaded or imported into the studio. Being in the Khronos sample collection makes it a useful test asset, not a normative humanoid naming convention.

The [glTF 2.0 specification](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#indices-and-names) defines joint/node references; node names are optional and need not be unique. It does not assign humanoid meanings to arbitrary node names. [VRM humanoid metadata](https://github.com/vrm-c/vrm-specification/blob/master/specification/VRMC_vrm-1.0/humanoid.md) does define semantic humanoid roles and could later supply a recognized mapping source. VRM parsing/material support is not included in this proposed first GLB unit. Existing canonical naming remains a compatibility path; do not adopt Cesium-specific labels as engine-wide vocabulary.

## Acceptance plan and open design work

Characterize current compatible GLB imports first. Unit-test mapping completeness, uniqueness, hierarchy, finite/invertible rest transforms, wrong fingerprint/version, missing bones, and ambiguous names. Verify the default character still works. Integration-test Cesium Man with a reviewed mapping and a second independently named rig or a renamed fixture, preserving extra bones. Exercise neutral pose, left/right arm bends and torso rotation on the same captured samples. Compare source animation in an independent viewer as an asset sanity check, without claiming that validates retargeting. Browser acceptance must show correction of an ambiguous mapping and useful errors.

Before implementation, inspect the actual Cesium GLB hierarchy/rest transforms and define supported topologies, how chest/neck chains are handled, explicit correction authoring, and compatibility with rig-specific saved clips. Do not promise arbitrary humanoid or non-humanoid rigs. This issue records the proposed direction and remaining work, not a universal importer already delivered.
